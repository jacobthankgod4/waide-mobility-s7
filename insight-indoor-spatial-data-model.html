Technical note · Indoor GIS

What a usable indoor spatial data model contains.

Most indoor mapping projects start with a drawing and end with a picture. A navigation system needs four layers underneath that picture, and a schema that lets each layer be queried and maintained.

By ThankGod Jacob Chibueze · Waide Mobility

A drawing answers a different question.

An architectural floor plan is designed to communicate construction intent. It shows walls, doors, dimensions and room names. It does not tell you which corridor connects to which lift, which entrance is open to the public, or how far it is from a parking bay to a store.

When a plan is imported into a navigation system without restructuring, the system inherits that ambiguity. The map looks correct and routes badly. The missing work is the data model: a set of layers, identifiers and relationships that express the building as a connected graph.

The four layers.

1. Levels

A level is not just an elevation. It is a container with a name, a public or private status, a vertical position and a set of connections to other levels. Names have to be stable, because signage, tenant lists and the interface all refer to them.

A minimal level record contains a stable identifier, a display name, a short code, an elevation or ordering value, and a list of connectors. The ordering matters: if Level 1 sits above Ground in one drawing and below it in another, the model has a contradiction to resolve before routing can be trusted.

2. Spaces

Spaces are the polygons people travel to: retail units, offices, wards, rooms, halls, service areas. Each needs a stable identifier, a name, a category, an access status and, where relevant, a tenancy reference.

The common mistake is to use the unit number as the primary key. Unit numbers get reused, renamed and split. A surrogate identifier with the unit number as an attribute survives a refit; a primary key based on the number does not.

Practical rule: identifiers should describe the record, not the current occupant. The tenant is an attribute with a validity period, not the identity of the space.

3. Connections

Connections are the vertical and horizontal links between levels and spaces: lifts, stairs, escalators, ramps and doors. Each connector carries attributes that routing depends on: direction, capacity, accessibility, operating status and, for a lift, the levels it serves.

This is where many indoor models are weakest. A lift drawn as a point symbol in a plan becomes an edge in the graph. If it is modelled only as a point, the router has no way to express the cost of waiting, the levels served, or the fact that the lift is out of service.

4. Route edges

The route network is a graph of nodes and edges over the walkable area. Nodes sit at decision points: junctions, doorways, lift lobbies, entrances, the ends of corridors. Edges carry a cost, a mode and an accessibility flag.

A good network has no orphaned edges, no edges crossing a wall, and no destination that is unreachable from a documented origin. Those three checks catch most of the failures that make a demo route look plausible and an operational route fail.

Separate networks, explicit transfers.

Vehicle and pedestrian movement are different graphs. A car park aisle is not a footpath, and a pedestrian corridor is not a road. Keeping them separate avoids routes that drive through a shopping concourse or walk down the middle of a parking ramp.

The two graphs meet at transfer nodes: a parking bay to a lift lobby, a drop-off point to an entrance. The transfer node is a modelled object, not an assumption. That is what allows a single journey to be described as a sequence of modes without conflating their costs.

What the schema has to support.

RequirementWhy it matters
Stable identifiersTenants, names and unit numbers change; references in other systems must not break.
Temporal attributesOpening hours, closures and tenancy periods affect whether a route is valid now.
Access classificationPublic, staff-only and emergency routes must be distinguishable at query time.
Accessibility flagsStep-free routing needs an explicit property, not an inference from geometry.
Level connectorsVertical movement is the hardest part of indoor routing and the easiest to omit.
ProvenanceEach feature should record whether it came from a plan, imagery or a field check.

The maintenance question.

An indoor model decays. Tenants change, fit-outs move walls, a corridor closes for refurbishment. If updating the model requires the original consultant, the model has a short operational life.

The schema should therefore be simple enough for a trained client team to maintain: clear feature types, a documented attribute list, an edit procedure and a review cycle. Complexity that only the builder understands is a delivery risk, not a mark of sophistication.

In the Novare Lekki pilot, the model was built in JOSM against an OpenStreetMap-style indoor schema. That choice keeps the data readable in open tools and makes the structure inspectable by another team. The trade-off is discipline: an open schema will happily accept inconsistent tagging, so validation rules have to be applied deliberately.

A short checklist.

  • Every space has a stable identifier independent of its current tenant.
  • Every level has a name, an order and a list of connectors.
  • Every connector states what it connects and whether it is step-free.
  • Every destination is reachable from at least one documented entrance.
  • Vehicle and pedestrian networks are separate, with explicit transfer nodes.
  • Every feature records whether it was drawn, observed or verified.
  • The client team can edit the model without the original supplier.

None of this is glamorous. It is the difference between a spatial model that survives contact with operations and a visualisation that is retired after the launch event.
