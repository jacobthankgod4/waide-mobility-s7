Technical note · Accessibility

Plan accessible routes before drawing the map

Step-free routes, useful destination details and screen-reader directions all depend on decisions made before the map is built. This note explains what to include.

By ThankGod Jacob Chibueze · Waide Mobility

Three decisions that cannot be retrofitted cheaply.

Most accessibility problems in a navigation system are structural, not cosmetic. They come from three early decisions: how routes are classified, what information is attached to a destination, and how the interface communicates direction.

1. Route classification

If the route network has one cost per edge and no accessibility attribute, there is no way to offer a step-free alternative. Retrofitting means rebuilding the graph, not adding a toggle.

A workable model carries, at minimum: a step-free flag, the type of level change, the width or clearance where known, and a status for temporary obstruction. These are attributes of the edge and the connector, not of the destination.

2. Destination information

"Accessible toilet" is not a sufficient destination. A person needs to know which level it is on, whether it requires a key, whether it is inside a tenanted area, and whether the route to it is step-free. The point-of-interest record has to carry those facts.

Content is part of accessibility. A screen reader can read a route perfectly and still leave the user without the information they need to complete the journey.

3. Interface behaviour

A map-first interface assumes the user can see the map. An accessible interface needs a parallel, text-first route: clear headings, ordered steps, distance and level information, and controls that work from a keyboard.

The two views can share the same routing service. They do not have to share the same presentation. Building the text route first often exposes gaps in the data that a map hides.

What to audit before drawing.

ItemQuestion to answerWhy it changes the model
EntrancesWhich are step-free, and when are they open?The route origin changes by time and by user.
Level changesWhich lifts and ramps are usable, and what do they serve?Vertical connectors carry the highest accessibility risk.
DoorsAutomatic, manual, width, threshold?A step-free corridor can still end at an unusable door.
FacilitiesAccessible toilets, assistance desks, quiet spaces?These are destinations in their own right.
SurfacesTactile paving, gradients, temporary works?Affects route suitability beyond step-free status.
AssistanceWhere can a person ask for help?A route that fails should have a fallback.

Testing with the people the system excludes.

Automated accessibility checks catch structural issues: missing labels, low contrast, keyboard traps. They do not catch a route that is technically step-free but passes through a crowded service corridor, or an instruction that is grammatically clear and spatially confusing.

Testing with disabled users is therefore not a public-relations step. It is the only reliable way to find out whether the route description works. Consent, scheduling and compensation should be planned into the project, not improvised at the end.

Where testing with users is not possible, the limitation should be stated. Claiming user validation that did not happen is worse than acknowledging the gap.

A minimum viable accessible model.

  • A step-free network that is separate from the standard network.
  • Explicit attributes on every level connector.
  • Accessible facilities recorded as destinations with conditions.
  • A text-first route view as well as a map view.
  • Keyboard operation and screen-reader announcements tested.
  • A route validation record that states what was checked on site.
  • An honest statement of what was not assessed or certified.

None of these guarantees a fully accessible venue. They do mean the digital system does not add a new barrier to the physical ones.
